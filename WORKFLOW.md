# Methods, execution order and input contracts

This document describes source behavior, not a validated reproduction. All paths below are relative to the separately authorised `VISITOR_LOGS_WORKSPACE`. Use a new data workspace, never the original research repository. Scripts can overwrite outputs, including the language-enriched event and session CSVs. Keep controlled backups outside the release. Scripts 09–14 and some diagnostics execute at import time; do not import them to inspect schemas.

Outputs are written under `data_clean/`, `dashboard_data/` and `outputs/`, with coordinate/calendar preparation also writing under `data_raw/`. All remain restricted. Even the reduced `sessions_dashboard.parquet` contains session-level information, not anonymous public data.

The dashboard requires nonempty `sessions_dashboard.parquet` and corrected coordinates. Session fields include `session_id,date,start_hour`, ticket language, duration, distinct-point count and event count (09 supplies dashboard aliases recognised by app.py). It optionally reads exhibit, action, language, context, ticket, holiday, weather, event and coverage Parquets named at the top of app.py. Missing optional files do not guarantee every callback works with every schema or empty dataset. Inventory is a name fallback; image is optional. No synthetic data or placeholder results are provided.

## Coordinate-entry tools

Both `visitor_map_clicker_v2/*.html` files are source tools, without embedded map or code lists. Use a separate controlled directory outside this release: copy the desired HTML there and supply only authorised map and coordinate/code files. Serve that directory on loopback with `python3 -m http.server 8000 --bind 127.0.0.1`. Never serve the research repository or the whole restricted workspace.

`map_clicker.html` reads `museum_map.png` and `t_codes.csv` (one `code` column), supports CSV import/export, and stores coordinates in browser localStorage. Supply actual pixel dimensions via `?width=WIDTH&height=HEIGHT`; private map dimensions were removed. It uses Leaflet 1.9.4 loaded from unpkg; network access and third-party code are required. Its y-axis is upward. Clear browser storage after authorised use.

`map_clicker_v3.html` reads `museum_map.png` and the `code` column of `coordinates.csv`, ignores old x/y values, derives natural image dimensions, and exports top-left-origin `coordinates_v2.csv`. Work is in memory until export; it does not automatically persist coordinates. Put exported files into the external paths required by 07c. Neither browser tool was exercised with maps or real codes. CSV parsing is simplistic; trusted, simple exhibit codes are assumed. UI interpolation is not hardened for arbitrary untrusted input.

## Method differences and interpretation

The earlier R workflow groups by card identifier, parses day-month-year timestamps and infers transitions between successive distinct points only for positive gaps below one hour. It counts interactions and daily distinct cards; it does not create the Python ticket-per-day sessions, infer ticket-language prefixes or join ticket/weather/holiday context. Its timestamp contract differs from Python's offset-bearing month-name log timestamps. Neither parser is a drop-in substitute for the other.

Python 04's device-per-day key is an exploratory interpretation superseded by 06's 18-character card-per-day key for the dashboard. The 18-character selection is a heuristic, not identity validation. Both can merge separate visits within one day or split a visit at midnight; repeated/reissued/shared tickets and maintenance events remain possible. Session duration is last minus first logged interaction, not total museum dwell time. Paths connect observed points, not continuous movement; consecutive repeat suppression varies by diagnostic. Action 0/1 labels are project-specific interpretations, not universal protocol semantics.

Stage 14 and dashboard plots distinguish missing observations from zero activity in several views. Date presence is a proxy for coverage, not proof of complete collection for a day. Context preparation often starts from log-summary dates, while the app assembles a fuller calendar from context sources; coverage and different views may use different denominators or date ranges. Sparse language/exhibit subgroups, joins with duplicate keys, timezone/DST handling, unknown codes and empty inputs need validation. Session/ticket ratios are descriptive, can exceed 100%, and do not estimate causal effects or validated visitor participation. Weather, holidays and events are contextual associations with confounding and incomplete coverage.
